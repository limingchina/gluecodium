# JVM C++ whole-file generation oracle

This tool invokes the installed, unchanged Kotlin `CppGenerator.initialize` and
`generate` on actual loader-produced models. It records every `GeneratedFile`'s
relative path, `MAIN` or `COMMON` source set and UTF-8 bytes, independently of
the native generator. No rendered context, include list, forward declaration,
sort result, name resolver result or predicate answer is recorded in a job.
The separate manifest is an expected output inventory, never generator input.

Java 17, an installed distribution at `gluecodium/build/install/gluecodium/lib`,
Python 3 and a C++17 compiler are needed. `JAVA_HOME` or `PATH` selects the JDK;
`CXX` selects the compiler. Run from any directory:

```sh
ruscodium/tools/cpp-generation-oracle/check
# After reviewing intended changes, replace the captures:
ruscodium/tools/cpp-generation-oracle/run
```

`check` compares all 315 production templates in the jar with their source,
regenerates each group in a **fresh JVM**, and compares the entire output file
set, source-set manifests, job JSON and bytes exactly. Each fresh process is
required because the template engine's copyright resolver is global. It then
compiles all generated `.cpp` files together with each checked-in consumer using
`-std=c++17 -Wall -Wextra -Werror` and runs both executables. The two generated
sets do not share a translation unit. `compile-consumers` accepts an optional root
with the same `GROUP/files/cpp` layout, so native outputs can be tested too.

Each `job.json` is a `gluecodium.cpp-generation-job` version 1 with the complete
version-1 `LimeModel` graph (including the reference map and auxiliary roots),
measured public getter views, checked absences, and options. `manifest.json`
contains only the output paths and source sets observed from `GeneratedFile`.
`files/` holds the original generated bytes. Every group contains all eighteen
helper/export files: thirteen common headers, three common implementation files,
the COMMON export header and the MAIN export header. Expected files are never
assembled from template fragments or native-generated data.

The `default` group loads [default.lime](default.lime) as main input with actual
`GeneratorOptions` defaults: empty root/internal namespaces, `_GLUECODIUM_CPP`
export, common export inherited from it, and null copyright. It has enum, alias,
lambda, interface, and struct roots; numeric and string values, map/nullable
fields, a string set, defaults, a field constructor, and readonly, mutable and
static properties. Two nested aliases occur in dependent-first source order;
the C++ generator moves the dependency first within the same alias collection. The `custom` group loads [custom.lime](custom.lime) as main and
[aux.lime](aux.lime) as an unreferenced auxiliary input. It uses root namespace
`acme::api`, internal namespace `acme::detail`, `ACME_API` and `ACME_COMMON`
exports, and a multiline copyright. Its renamed class, reordered nested alias
and struct, class forward declaration, nested-type include, cross-root references
and generic fields exercise ownership and option-dependent paths. Consumers define
concrete interface/class implementations and exercise generated constructors and
methods. The auxiliary declaration remains available for lookup but owns no
output. Files with generated parameter documentation can occur even with
comment-free LIME input.

The overlay allowlist records actual public getter results only: `name` and
`fullName` on `LimeNamedElement`; `actualType` on `LimeType`; `isEmpty` on
`LimeComment`; `isVoid` on `LimeReturnType`; `exception` on `LimeFunction`;
`uniqueEnumerators` on `LimeEnumeration`; `uninitializedFields` on `LimeStruct`;
and `fields` and `struct` on `LimeFieldConstructor`. Getter-discovered objects
are traversed to closure. The new incremental snapshot API reads each node's
properties once, so getters returning newly allocated views cannot expand the
same node indefinitely; the existing snapshot API is unchanged. The checked
absence candidates are `propertyElement`, `isVirtual`, `isConst`,
`isAsyncHelper`, `internalNamespace`, `exportName`, `functionUsings`,
`needsExport`, `storageQualifier`, `structElement`, `struct`, `iter`, and
`constructorComment`; a candidate is recorded per model element only after
confirming no public zero-argument bean accessor exists. These are frontend
views, not generated decisions. Nonempty user documentation and broader LIME
features are outside the fixtures' demonstrated scope.

## Raw documentation profile

`run-docs` captures version-2 jobs in a separate directory and `check-docs`
regenerates their complete output sets, compiles every generated implementation
with strict C++17 flags, and runs three consumers. The `docs` real-LIME fixture
covers Unicode, paragraphs, platform selection, configured placeholder text,
exclusion, functions, properties and struct/field-constructor documentation.
The other two groups load unmodified upstream `CommentsInterface.lime` and
`CommentsLambda.lime` independently; neither represents the complete comments
smoke scenario.

The opt-in `CPP_ORACLE_RAW_COMMENTS=1` profile reflectively reads the private
`LimeComment.taggedSections` field, checking its shape and exporting one ordered
array of `[tag,text]` string pairs for every comment node, including empties and
placeholder nodes. The snapshot stays version 1; the generation job is version
2 and does not supply comment `isEmpty` overlays. Paths, exclusions and
placeholder references remain in the snapshot. The oracle never exports selected
or formatted comment text. Ordinary loader placeholder values are parsed without
nested placeholder mappings, so the fixture uses the loader-supported one-level
case; deeper recursion must be labeled synthetic model evidence. Default/custom
version-1 captures and the reference-model exporter remain unchanged.
